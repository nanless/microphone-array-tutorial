1. Audio Capture, Clocking, and Continuous Streams

I01: PortAudio Callbacks and Hardware Timestamps

PortAudio provides a cross-platform C abstraction over host audio backends. This repository pins the commit corresponding to release 19.7.0. Begin with the callback signature in include/portaudio.h, then inspect the capture and playback examples under examples/; although PortAudio itself uses the MIT License, host OS backends carry their own platform dependencies. Official callback guidelines strictly forbid operations with unbounded or unpredictable latency—such as dynamic memory allocation, file I/O, mutex locking, or console printing—inside the real-time audio callback.

Every hardware test log must record the active host API, device ID, sample rate, sample format, channel count, requested vs. negotiated latency, and callback block length. Note that frameCount denotes time samples per channel—never multiply frameCount by channel count and mistake the scalar sample total for a frame count. Log input ADC timestamps, output DAC timestamps, and callback status flags; never treat timestamps across two distinct physical devices as sharing a common clock without explicit calibration.

End-to-end latency acceptance can inject an acoustic or electrical loopback impulse while stressing disk I/O and CPU load, correlating callback status flags, inter-callback intervals, ring-buffer occupancy, and audible dropouts. A conservative architecture copies callback frames into pre-allocated lock-free ring buffers, though bounded real-time DSP with verified worst-case execution time may run in-callback; blocking Python inference or synchronous logging must never sit on the callback thread. After hot-unplugging and reconnecting a USB array, re-verify physical channel mapping rather than merely re-opening the previous numeric device index.

Pinned portaudio.h permits paFramesPerBufferUnspecified, under which frameCount varies dynamically from callback to callback. Real-time factor (RTF) must divide processing time by the newly arrived audio duration frameCount / sampleRate; similarly, overlapped STFT pipelines must normalize compute budget against the hop duration of newly arrived samples rather than inflating the denominator to the full analysis window length (which reuses historical samples). Hardware callback blocks, algorithm hop sizes, and playback blocks can be decoupled cleanly via bounded FIFO queues without forcing all stages onto a giant least-common-multiple buffer.

Crucially, paInputOverflow signals only that input samples were dropped—it does not provide a portable, exact dropped-sample count. Under fixed-size callback buffers, upstream documentation notes that dropped samples may fall at one or multiple interior positions within the delivered buffer, whereas variable-size buffers place drops prior to the first sample. Status flags, timestamps, hardware sample counters, and stream restarts must all be logged separately: record an exact dropped-sample count only when corroborated by independent hardware counters, and otherwise log "discontinuity_detected, dropped_samples=unknown"—never substituting 0 and pretending AEC or resampler states remain phase-continuous.

Log timestamp tap points alongside their exact sample-index correspondence. Official PaStreamCallbackTimeInfo exposes three distinct instants in seconds on the stream's clock: inputBufferAdcTime (ADC capture instant of the first sample in inputBuffer), currentTime (instant the callback was invoked), and outputBufferDacTime (DAC playout instant of the first sample in outputBuffer). Subtracting outputBufferDacTime - inputBufferAdcTime yields true end-to-end sample latency only when both belong to the same clock domain and you track which input sample maps to which output sample. If a worker thread defers output emission by one callback block, the sample-index offset shifts by one block as well—one cannot keep subtracting the two first-sample timestamps of the same callback invocation.

Exercise E10-17 works out by hand a 15 ms input age plus 30 ms output lead yielding 45 ms corresponding-sample latency—rising to 55 ms when queued one extra 10 ms block—and shows why 3 ms of in-window compute sitting between those two hardware instants must NOT be double-counted. PortAudio's Buffering, Latency and Timing Implementation Guidelines further caution that some host backends report only partial/nominal driver buffering, so struct fields never substitute for physical loopback impulse verification (no soundcard was opened in E10-17).

I02: ALSA PCM State Machine and XRUN Recovery

On Linux, device-level behavior can be audited directly in alsa-project/alsa-lib via src/pcm/pcm.c and test/pcm.c. Root COPYING specifies LGPL-2.1, with per-file headers governing exact version clauses and exceptions. ALSA's PCM (Pulse-Code Modulation) API cleanly separates hardware ring-buffer parameters (hw_params), software start/wakeup thresholds (sw_params), and runtime stream states.

The official ALSA PCM documentation distinguishes error codes by root cause: -EPIPE signals playback underrun or capture overrun (XRUN); -ESTRPIPE indicates system suspend; -ENODEV indicates physical device removal; and hardware echo-reference loopback subdevices may return -ENODATA when the paired playback stream has not yet started. Calling a single blind recovery wrapper on every negative return code—and assuming sample continuity afterward—breaks downstream stateful DSP.

Deployment specs must pin period_size, buffer_size, avail_min, start_threshold, interleaved vs. non-interleaved access layout, and monotonic timestamping mode. Test short reads/writes, SIGSTOP/SIGCONT process stalls, OS suspend/resume, USB hot-unplugging, and opening the echo-reference capture stream before starting far-end playback. After any XRUN recovery, log a stream discontinuity event, report an exact lost-sample count only if hardware frame counters or monotonic timestamps uniquely determine the gap (recording the derivation basis), and notify AEC, resamplers, and trackers to reset or re-align—calling snd_pcm_prepare() restarts DMA without magically restoring lost acoustic history. No Linux soundcard or hot-plug hardware tests were executed here.

I03: PipeWire's Four AEC Streams

PipeWire's canonical repository resides on freedesktop GitLab, mirrored officially at PipeWire/pipewire on GitHub. Key entry points are src/modules/module-echo-cancel.c and spa/plugins/aec/aec-webrtc.cpp. Root COPYING is MIT, while optional WebRTC audio-processing backends carry their own licenses.

PipeWire 1.6.9 module-echo-cancel documentation separates four distinct graph streams: physical microphone capture, virtual echo-cancelled source exposed to applications, virtual sink receiving application audio, and physical loudspeaker playback. Any system audio intended for cancellation must traverse the designated reference path; monitor.mode alters how the reference tap is acquired, so audio.rate, channel map, target node bindings, and node.latency must all be archived alongside a dump of the active PipeWire graph.

In pinned meson.build, PipeWire selects dynamically among webrtc-audio-processing-2, -1, or legacy system libraries at build time—never assume PipeWire runs the exact same WebRTC AEC3 commit pinned elsewhere in this book merely because both say "WebRTC." Moreover, in this pinned commit, aec-webrtc.cpp enables high-pass filtering and noise suppression by default, disables AGC, and passes (num_blocks - 1) * 10 ms as the nominal stream delay to WebRTC APM rather than querying hardware DAC/ADC timestamps. Consequently, any benchmark comparing a PipeWire virtual mic against direct in-app WebRTC APM must record the distro library version, submodule toggles, num_blocks, reference routing, and exact output tap rather than attributing every difference to the linear AEC core.

Verify that VoIP speech, OS notification chimes, and media playback all enter the reference sink, and re-verify after switching default output devices (e.g., speakers to HDMI/Bluetooth). Inject reference dropouts and playout-delay steps to observe recovery. Crucially, when the OS sound server already runs AEC, enabling a second in-app AEC alters residual statistics and compounds near-end speech distortion—always compare single-AEC vs. cascaded-AEC configurations rather than merely checking that a virtual microphone node appears.

When an application embeds pinned WebRTC Audio Processing Module (APM) directly instead of relying on PipeWire, follow api/audio/audio_processing.h: feed far-end render frames destined for the loudspeaker into ProcessReverseStream(), call set_stream_delay_ms() with the current hardware buffer delay immediately before each capture frame, and then invoke ProcessStream(). Externally, APM operates on 10 ms linear PCM frames—channel-interleaved for int16_t APIs and deinterleaved per-channel pointers for float APIs.

At pinned commit 0467d2b91cc20b9b001c2bbb73d43ea6b2491f3e, the int16_t overload restricts sample rates strictly to 8, 16, 32, 48 kHz (NativeRate), requiring identical rates across capture input, capture output, and reverse render streams plus matching capture I/O channel layouts; the float overload accepts arbitrary valid rates and distinct I/O channel counts. Thus 44.1 kHz integer PCM cannot enter the int16_t overload directly without resampling or switching to the float interface; see Initialize() constraints and NativeRate enum.

Note that set_stream_delay_ms() represents the sum of render buffering after ProcessReverseStream() until physical DAC output plus capture buffering after physical ADC input until ProcessStream()—never room acoustic time-of-flight or WAV header metadata.

In pinned audio_processing_impl.cc, delay arguments outside [0, 500] ms are clamped to [0, 500] ms with a warning return code; always log the requested delay, return status, and read-back stream_delay_ms(). To compare linear adaptive cancellation against post-nonlinear suppression, set echo_canceller.export_linear_aec_output = true and call GetLinearAecOutput() right after ProcessStream(): because that exported linear tap is fixed at 16 kHz (160 samples per 10 ms block), never splice or diff it naively at 48 kHz device rate. See Enhancement Guide A06 for full AEC3 internals.

Audit playout-volume notifications separately from reference waveforms. In pinned WebRTC, CreatePlayoutVolumeChange() posts an unnormalized integer volume notification; on the capture side, detecting a change propagates a boolean gain_change flag rather than applying sample-wise gain compensation to the reference buffer. Inside refined_filter_update_gain.cc line 52, the gain_change branch remains an explicit TODO alongside ERLE-estimator state resets—so it must never be described as automatic filter rescaling. Always record whether volume scaling occurs upstream or downstream of the AEC reference tap alongside exact sample indices of volume steps; see Enhancement Guide A06 (static source re-verification only; zero new hardware or C++ runs).

I04: Stateful Sample-Rate Conversion in libsamplerate

libsndfile/libsamplerate identifies version 0.2.2 in its README under the BSD-2-Clause license. Core state lifecycle functions src_new, src_process, and src_reset reside in src/samplerate.c, backed by polyphase sinc/interpolator kernels under src/.

The Full API specification defines src_ratio = output_sample_rate / input_sample_rate and returns per-call input_frames_used and output_frames_gen. Callers must neither assume 100% consumption of every input buffer nor instantiate a fresh SRC_STATE per chunk. On the final input buffer, set end_of_input = 1 and continue invoking src_process on the same state with zero new input until output_frames_gen == 0 to drain internal FIR history; merely rewriting a WAV header's sample rate or halting as soon as input samples run out violates the streaming protocol.

When SRC_DATA.src_ratio changes between consecutive src_process calls, libsamplerate linearly interpolates the conversion ratio across the output block; conversely, calling src_set_ratio() forces an immediate step to the new ratio on the next block, bypassing linear slewing. Because the two APIs serve distinct control objectives, updating a ratio field never substitutes for blind clock-drift estimation or artifact-free phase tracking; see the Set Ratio section of the Full API.

Under this book's SRO sign convention, a capture clock running +100 ppm fast (16001.6 Hz vs. 16000 Hz) requires resampling ratio 1 / 1.0001 ≈ 0.99990001 to align onto the nominal reference clock. Validate whole-utterance vs. chunked streaming residuals after compensating fixed FIR group delay, measure stopband alias rejection near Nyquist, and test abrupt steps, slewed ratio updates, and multi-hour FIFO occupancy—a matching file duration over a few seconds never proves long-term phase coherence.

To verify the C streaming contract concretely, this repository executes a re-runnable libsamplerate SRO experiment on a 10 s mono synthetic impulse train: relative to a 16 kHz reference clock, the simulated capture clock runs +100 ppm fast (16001.6 samples/s) during 0–5 s and +150 ppm fast (16002.4 samples/s) during 5–10 s, with impulses placed at exact reference instants 1, 3, 4, 6, 8, 9 s. Integrating piecewise clock rates and rounding yields 160020 captured frames, with an analytical uncompensated drift increment of 16 frames between the 1 s and 9 s impulses. Crucially, the piecewise clock rates here are oracle ground truth supplied directly to the resampler, NOT estimated blindly from audio.

From Stationary Noise Floors to Controlled Online Noise Tracking

When background noise rises mid-call, freezing an initial noise estimate $D_f$ leaves unattenuated residual noise, whereas blindly averaging every active speech frame into $D_f$ cancels target speech. MCRA (Minima Controlled Recursive Averaging) solves this by modulating the update rate of the noise power estimator itself: reading page 13, Sections II–III, Eqs. (3)–(14) of Cohen and Berdugo's 2002 IEEE SPL paper (verified 2026-10-01) traces conditional noise updates, smoothed speech-presence probability, time-frequency local averaging, two-window running minima tracking, and ratio thresholding—far richer than multiplying a final Wiener gain by a binary VAD bit.

Given speech-presence probability $p_t \in [0, 1]$ and baseline noise smoothing factor $\alpha_d$, MCRA forms the time-varying smoothing factor $\widetilde{\alpha}_t = \alpha_d + (1 - \alpha_d)p_t$. For $\alpha_d = 0.8$, previous noise power 2, and current noisy power 10 (in identical linear power units at a single bin), $p_t = 0$ updates noise power to 3.6, whereas $p_t = 0.9$ slows the update to 2.16. That single-step conditional recursion is exercised over multi-frame sequences in Exercise E10-21, while full minima-tracking and two-iteration IMCRA bias compensation are analyzed in Spatial Processing §§50–51.

Not every C library implements soft-probability MCRA: in pinned SpeexDSP (preprocess.c), preproc_update_prob sets a hard binary flag per bin whenever $0.4 S > S_{\min}$, and preproc_noise_update updates the noise estimate only when that flag is 0 or when current power falls below the previous noise estimate. Our bounded native helper test in I32 confirms downward noise tracking even while flagged, without mislabeling Speex's heuristic as full Cohen MCRA/IMCRA. (Visiting Israel Cohen's software page yielded no license-verified redistributable archive during our check, so we cite the published equations without redistributing author MATLAB scripts.)

Inspecting lines 461–488 of ladspa/src/lib.rs reveals a second timing assumption in that same latency-reduction branch: it checks t_proc_change > 10 * sr / frame_size while incrementing t_proc_change += 1 once per host run(sample_count) callback rather than accumulating sample_count or elapsed wall-clock seconds.

At sr = 48000 Hz and model hop frame_size = 480 samples, the threshold RHS equals 1000. Output Stream Slots vs. Speaker Identities Govern Which WER Metric Applies

Section 3.2 Eq. (3), Sections 3.3–3.5, and Figure 1 of the MeetEval paper (v3, 2024-01-25) separate speaker-attributed diarization streams from unattributed continuous speech separation (CSS) slots: cpWER optimizes a single global bijection between reference speakers and hypothesis streams across an entire session; ORC-WER (Optimal Reference Combination WER) assigns each intact reference utterance to an output stream while preserving intra-speaker/reference utterance order; and MIMO-WER generalizes assignment across multiple input/output streams while preserving each reference speaker's internal utterance order.

Because a 2-output CSS front end reuses its two output slots across $>2$ meeting participants over time (CSS ICASSP 2020 paper §§1–2), suppose speakers A and B overlap saying "a" and "b", followed later by speaker C saying "c", and CSS cleanly outputs slot 0 = "a c", slot 1 = "b". Every word is preserved without crosstalk, so ORC-WER = 0; yet feeding those two CSS slots directly into cpWER (padded with an empty third hypothesis speaker) incurs 1 deletion and 1 insertion on "c", yielding $\text{cpWER} = 2/3$. Thus cpWER penalizes lack of speaker diarization rather than acoustic separation failure—and conversely, ORC-WER forbids splitting reference utterance "b c" post-hoc into "b" and "c" to artificially lower errors against "a b" / "c" (whose true ORC error count is 2).

Nor does DI-cpWER measure speaker-identification accuracy directly: in pinned di_cp.py, greedy_di_cp_word_error_rate swaps reference and hypothesis roles inside greedy ORC before swapping insertion/deletion counts back—yielding a greedy upper bound rather than an exact optimum (and note that the pedagogical di_cp_lev snippet inside upstream's doc/simplified module contains a parameter/variable typo raising NameError when invoked directly, an isolated doc-function bug kept distinct from the Cython-backed production entry point).

Utterance Granularity, Word Timestamps, and Diagnostic Metric Boundaries

Reading Sections IV-F, V-A Eq. (10), VI-A, and VII Algorithm 1 of the authors' follow-up manuscript Word Error Rate Definitions and Algorithms for Long-Form Multi-talker Speech Recognition (2025, v1) (supplemental verification 2026-10-02) reinforces three rules: (1) reference utterance boundaries are fixed evaluation inputs (Exercise E11-16); (2) DI-cpWER is a diagnostic tool rather than a primary leaderboard metric because re-segmenting hypotheses alters assignment degrees of freedom; and (3) standard Levenshtein ignores timestamps completely—matching reference word "spring" on [0, 1] s against hypothesis "spring" at [10, 11] s with 0 errors, whereas time-constrained Levenshtein rejects disjoint intervals (1 deletion + 1 insertion = 2 errors) while matching overlapping [0, 1] s and [0.5, 1.5] s with 0 errors (Exercise E11-17, operating on pre-tokenized whole words).

Pay close attention to boundary-touching intervals in pinned levenshtein.h::overlaps (line 94): upstream tests two strict inequalities (a_begin < b_end && b_begin < a_end). I23: libebur128 Integrated Loudness and True Peak

Peak-limiting AGCs bound sample amplitude, yet do not regulate audio volume according to human loudness perception. jiixyj/libebur128 provides loudness and peak metering via ebur128/ebur128.h and ebur128/ebur128.c. The version macro in the pinned snapshot is 1.2.6, and root COPYING specifies the MIT License; bind implementations and metering modes strictly to this commit rather than claiming full standards certification across every configuration merely because the library name mentions R128.

Momentary loudness, short-term loudness, and integrated loudness operate over distinct statistical time windows; Loudness Range (LRA) characterizes temporal variability, while sample peak and true peak inspect waveform amplitude. In the C API, integrated loudness is returned in LUFS (Loudness Units relative to Full Scale), whereas ebur128_true_peak returns linear full-scale amplitude—converting to dBTP (decibels True Peak) requires taking $20\log_{10}$ relative to digital full scale. Neither quantity substitutes for the other, and neither yields acoustic dB SPL without physical microphone sensitivity calibration.

The underlying measurement algorithm follows ITU-R BS.1770-5 (approved 2023-11-22, verified in force on the official ITU page on 2026-09-28). A metering standard does not automatically dictate target loudness for every product: items g–m on pages 3–4 of EBU R 128-2023 address broadcast programme delivery—specifying whole-programme integration, a -23.0 LUFS target, and a -1.0 dBTP ceiling in linear PCM production alongside delivery tolerances. Never copy broadcast mastering targets blindly as default AGC setpoints for ASR, VoIP telephony, or wake-word front ends (the ≈ -23 LUFS sine probe below simply reflects the amplitude of 0.1 chosen for that test stimulus).

Initialize the desired metering modes via ebur128_init, then stream interleaved audio continuously. Frame counts passed to ebur128_add_frames_* denote time frames per channel, not total scalar samples across channels. Channel role assignments directly weight loudness summation: because the header's default channel map assumes standard surround/programme speaker layouts, never feed four raw microphones of an array directly as four surround programme channels. Measure a single enhanced output stream as mono CENTER, and maintain separate single-channel meter instances when comparing individual microphones.

Two-stage gating determines which time blocks enter integrated loudness, so digital silence or sub-threshold signals can return -inf. Callers must record meter state, active duration, and undefined/failure reasons explicitly—never clamping -inf to 0 LUFS and averaging it into corpus means. Likewise, true-peak oversampling estimates reconstructed inter-sample waveform crests that can exceed the maximum stored discrete sample magnitude, so unclipped sample peaks alone do not guarantee D/A headroom.

Recommended protocol check: feed a sufficiently long, steady-amplitude non-silent signal well above the gating threshold, then scale the entire waveform by 0.5. Provided the gated active region remains identical, integrated loudness drops analytically by $20\log_{10} 2 \approx 6.0206$ LU while both sample peak and linear true peak halve. Test digital silence, short clips, per-chunk state resets, and misassigned channel maps separately (verifying metering contracts rather than subjective listening quality).

I33: Signal Model and Convergence Guarantees of Original DANSE

Align notation first between Bertrand & Moonen's 2010 two-part IEEE TSP papers—Part I: Sequential Node Updating (10.1109/TSP.2010.2052612) and Part II: Simultaneous and Asynchronous Node Updating (10.1109/TSP.2010.2052613)—and Chapter 13 of this textbook (where $K$ in Part I/II is NOT node count):

Mathematical Quantity DANSE Part I / II Notation This Book (Chapter 13)
Number of sensor nodes $J$ $U$
Broadcast / compressed dimension per node $K$ $Q$
Shared latent target source dimension $Q$ $S$

Thus upstream's dimension condition $K = Q$ corresponds to $Q = S$ here: on a shared frequency bin and sample timeline, node $u$ observes $\vec{x}_u$ and targets $\vec{d}_u = \mathbf{B}_u \vec{s}$ for a common latent source vector $\vec{s}$ (requiring nonsingular square $\mathbf{B}_u$ when $Q = S$). Centralized LMMSE solves $\mathbf{R}_{xx}\mathbf{W}_u^\star = \mathbf{R}_{x d_u}$; in DANSE, node $u$ stacks its raw local channels $\vec{x}_u$ with $Q$-dimensional compressed broadcasts from peer nodes, solves a local LMMSE system, and updates its future outgoing broadcast compressor from the local sensor block of its own weight matrix—broadcasting linear combinations of raw local observations only rather than re-broadcasting fused outputs containing remote signals (Part I §§II, III-A, IV-A, Theorems III.1 & IV.1).

Sequential convergence theorems assume nonsingular $\mathbf{R}_{xx}$, full-rank shared-subspace transforms $\mathbf{B}_u$, exact stationary second-order statistics, and round-robin updates—proving that adaptive $Q = S$ compression attains centralized LMMSE, NOT that arbitrary fixed beamformers are lossless (§13.8 provides an explicit spatially correlated noise counterexample), nor guaranteeing optimality under $Q \lt S$ compression loss, finite-snapshot VAD errors, or rank-deficient pseudoinverse regimes (Part I §IV-C: DANSE Under Rank Deficiency).

Under simultaneous node updates, peer broadcast compressors change concurrently. In Part II §IV-B Eqs. (22)–(28), pp. 5297–5298, $rS\text{-DANSE}^+$ introduces an auxiliary subspace optimization over $\mathbf{G}$, and Theorem IV.1 requires diminishing step sizes $0 \lt \alpha_i \le 1$, $\alpha_i \to 0$, $\sum_i \alpha_i = \infty$ alongside exact statistics; simplified §IV-C $rS$-DANSE (omitting $\mathbf{G}$ optimization and using constant $\alpha = 0.5$ or $0.7$) is an empirical relaxation that cannot invoke Theorem IV.1. Meanwhile, Part II §IV-D's parameter-asynchronous DANSE permits irregular filter update instants across nodes while still requiring persistent per-node updates and sample-level clock synchronization (Footnote 8).

I36: RTP Timestamps, Reference Clocks, and Dante Platform Boundaries

Separate packet NIC arrival time, first-sample ADC timestamp, and scheduled playout time. In RFC 3550 §5.1 & §6.4.1, RTP sequence numbers increment per packet while RTP timestamps mark the first audio sample on a stream's media clock starting from a random offset—so raw RTP timestamps across two nodes cannot be subtracted directly without RTCP Sender Report (NTP, RTP) mappings, RFC 3550 interarrival jitter is packet network jitter rather than crystal ADC ppm, and sequence-number gaps require payload/timestamp inspection to determine exact lost sample counts.

Similarly, RFC 7273 §§4–6 separates timestamp reference clocks (ts-refclk) from media sample clocks (mediaclk): disciplining an OS wall clock via PTP never proves that an asynchronous USB/I2S audio ADC crystal is hardware-locked to that PTP clock.

Audinate's Dante Controller Clock Synchronization and Dante Latency pages document leader/follower clocking (PTPv1 by default, plus PTPv2 when AES67/RTP is enabled; hardware PLLs or external word clock on dedicated Dante silicon vs. host computer clocking on Dante Virtual Soundcard) and deterministic playout latency (max(tx_setting, rx_setting), with larger minimums on general-purpose PCs)—platform-specific guarantees that never transfer automatically to commodity Wi-Fi UDP streams (no Dante hardware or PTP network was connected here).

I37: Compute Payload Bitrates First Before Budgeting Link Bandwidth

With $U$ nodes, $M_u$ local mics per node, and $Q$ real time-domain PCM broadcast channels at rate $f_s$ and $b$ bits/sample, raw node payload is $f_s b M_u$ bit/s vs. compressed payload $f_s b Q$ bit/s (768 vs. 256 kbit/s for 16 kHz, PCM16, $M_u = 3, Q = 1$).

Across $U = 4$ nodes, pairwise unicast transmits $U(U-1) = 12$ streams (3.072 Mbit/s), true single-send broadcast/multicast emits $U = 4$ streams (1.024 Mbit/s), and tree up-sum + down-broadcast sends $2(U-1) = 6$ directed edge streams (1.536 Mbit/s, Exercise E13-16, plus $8 Q^2$ bytes per complex64 $Q \times Q$ matrix update).

Overlapped STFT streams (512 FFT, 256 hop = 62.5 frames/s at 16 kHz, 257 one-sided complex64 bins) carry $257 \times 8 \times 62.5 = 128500$ B/s = 1.028 Mbit/s per channel before framing metadata (Exercise E13-09).

Adding explicit L3/L4 packet headers to 10 ms (160-sample = 320 B) mono PCM16 packets—12 B base RTP header (RFC 3550 §5.1), 8 B UDP header (RFC 768), and 20 B optionless IPv4 header (RFC 791 §3.1)—yields 360 B $\times 100\text{ pkt/s} = 288$ kbit/s (+12.5% over 256 kbit/s payload, still excluding Ethernet/VLAN/802.11 MAC contention/retransmissions/SRTP/PTP, and always evaluated alongside compression subspace loss, quantization noise, and jitter-buffer packet-drop rates).
